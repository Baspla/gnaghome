# Product roadmap and backlog

**Status:** Product direction captured from the user; this is a planning backlog, not a delivery schedule or implementation specification. No priorities or dates have been agreed. An unchecked box means the item is listed here, not that its current implementation state has been audited.

This roadmap describes the intended apps, shared platform systems, and integrations for Gnaghome. Keep the backend a self-hostable modular monolith: apps own their product data and authorization, platform systems provide reusable capabilities, and integrations connect external providers through explicit contracts.

Each item below notes its likely enabling dependencies and possible later connections. These are capability relationships, not a priority order or a claim that every optional connection is planned; where scope is undecided, that is called out explicitly.

## Apps

- [x] **CrewNow** — Implemented as a camera-based photo app with two immutable post images (front and back camera), an optional caption, and people-on-the-photo tags selected from Gnaghome users. The caption and tag picker appear after capture; uploads start immediately in parallel and remain pending/private until publication, while retake/cancel discards unreferenced pending images. Authors can create, edit captions/tags, and delete; any authenticated Gnaghome user can browse a cursor-paginated timeline or an individual post. Posts use the shared Files platform; post creation records one `crewnow.image_posted` activity, whose feed rendering resolves the post's current tags so edits update the sentence without creating another activity. CrewNow posts and their feed items use the same Discussions platform thread; comment counts appear in the activity feed, and the post page has the shared realtime comments component. Timelines, feed items, and discussion panels recover from invalidations/reconnects. No posting timers/limits, notifications, reactions, or reference-app visual design are included. **Depends on:** Files, local user identity, Activity Feed, Discussions, and backend-owned post/tag authorization.
- [ ] **Archive** — Port/integrate the existing codebase for a library of user stories. **Depends on:** local user identity and the app's own story access rules. **Optional later:** Files for story media, and Activity feed, Discussions, or Reactions if stories are made shareable/social.
- [ ] **Stats** — Build visualizations over activity collected from external services. Prefer consuming persisted activity through a defined contract rather than coupling charts directly to provider integrations. **Depends on:** External user activity and at least one inbound data integration; Tasks are needed for the planned background sync path. **Optional later:** Profiles for user presentation and Newsletter as another consumer of the same activity data.
- [ ] **Games** — Port/integrate the existing codebase to show which games people own and help a group find games to play together. Confirm which providers and ownership data the first version needs. **Depends on:** local user identity/access rules and an ownership-data source; a provider such as Steam is needed if selected as that source. **Optional later:** External user activity for game-related activity, and Activity feed or Notifications for group updates.
- [ ] **Calendar** — Add a group calendar. **Depends on:** local user identity and the app's group-sharing/access rules. **Optional later:** Activity feed for generated event-start items, and Notifications (possibly Tasks for scheduled reminders); neither is required to build the calendar itself.
- [ ] **Reviews** — Let users review things they like or dislike. Decide which kinds of things can be reviewed and whether reviews are ratings, written comments, or both. **Depends on:** local user identity/access rules and a defined reviewable target or catalog. **Optional later:** Discussions and Reactions for separate social interaction, and Files for review attachments; these do not determine the review/rating model.

## Shared platform systems

- [x] **Profiles** — Initial profile presentation is implemented on the existing local user identity/profile foundation: authenticated `/profile/<id>` pages show the user's profile picture, name, and account creation date, with reusable `Username` and `ProfilePicture` components. Further profile customization remains future work. **Depends on:** local user identity/profile data. **Optional later:** Files if avatars move to shared file storage, and Profile customization and cosmetics.
- [x] **Files** — Implemented as a general-purpose shared way to upload and retrieve images. Bytes are stored on local disk beneath the backend's Docker-persisted data volume and metadata in SQLite. Authenticated `/api/v1/files/<id>` URLs serve the image inline. Uploads start pending, private to the uploader, and expire after 24 hours; the uploader can preview a pending image, while other users cannot read it until its owning app finalizes it after persisting the resource reference. Finalization is an internal, idempotent service call that clears expiry and sets ready-file visibility. Startup and hourly cleanup remove expired pending files, retrying interrupted deletion; app-triggered deletion also marks the file deleting first so cleanup can retry a failed storage operation. Ready non-private files are readable by any signed-in Gnaghome user; ready private files are uploader-only. No generic HTTP delete/finalize endpoint is exposed; the owning app handles its resource references and authorization before calling Files internally. The initial accepted formats are PNG, JPEG, GIF, WebP, AVIF, and APNG, verified from file contents; uploads are capped at 10 MiB. This is not a CrewNow-only system. **Optional later:** other media types, shared folders/general-purpose file management, image transcoding or EXIF stripping, and apps such as CrewNow, Archive, Reviews, or Custom emoji using Files as their needs arise.
- [ ] **Tasks** — Provide durable asynchronous jobs for work such as fetching a Steam data snapshot, including the appropriate persistence, retry, and failure visibility for a small self-hosted deployment. **Depends on:** durable persistence and a job execution mechanism. **Optional later:** Notifications for job/failure reporting or Audit log records for operationally significant actions; neither is required for a basic job runner.
- [ ] **Activity feed** — Provide a central feed of app and system activity, such as someone posting a CrewNow image, updating a profile, a calendar event starting, or a user's birthday. Store typed activity records rather than rendered free-text sentences: an event type, an optional actor user ID, an optional subject user ID, timestamps, and validated type-specific data. An optional target is identified by its type and ID (for example, `crewnow.post` plus the post ID); no separate app field is needed. The owning app resolves targets and enforces viewer access. Begin without discussions or reactions. Distinguish recorded user actions from generated or recurring items such as birthdays and calendar starts, whose creation and visibility rules may differ. **Depends on:** durable storage, local user identity where actor/subject attribution applies, and app contracts for publishing events and resolving/access-checking targets. **Optional later:** Discussions and Reactions on the same canonical targets; neither is needed for the initial feed.
- [ ] **Audit log** — Durably record actions across apps and platform systems, including creations, updates, and deletions, for administrative oversight. Audit records are separate from social activity-feed items and external user activity, and only admins may view them; enforce this on the backend. **Depends on:** durable storage, actor identity, and audit-recording contracts from participating apps/systems, plus backend admin authorization for reads. **Optional later:** Notifications for selected administrative alerts; it is not a dependency on the Activity feed or External user activity.
- [ ] **External user activity** — Persist activity collected from external services in a form that apps such as Stats can query. Define provider-to-platform contracts, user/account attribution, retention, and deletion behavior. Decide whether derived aggregates or visualization-oriented processing belong here or in consuming apps; this provider activity is distinct from app-generated feed items. **Depends on:** inbound provider integrations, linked-account-to-local-user mapping, and durable persistence. Tasks support the planned background collection/sync path. **Optional later:** Stats, Newsletter, or other consumers; derived aggregates may be added here or remain consumer-owned, as yet undecided.
- [ ] **Notifications** — Provide a unified, user-scoped way for apps to create and retrieve notifications, with delivery adapters such as web push, Discord, email, and ntfy. Keep durable notification state separate from delivery; define adapter configuration and user preferences as part of the design. **Depends on:** local user identity/preferences, durable notification state, and delivery adapters for whichever channels are enabled. **Optional later:** Tasks for retries or scheduled delivery and app integrations with the service; no single app or feed is required to establish the core system.
- [x] **Discussions** — Implemented as a reusable platform capability with one discussion per namespaced target and persisted messages. Any authenticated user can comment; only the author can edit or delete. Edits receive an `edited_at` timestamp. Authenticated API reads/writes require a consuming app's target-visibility callback; CrewNow is the first integration. The shared comments UI subscribes to content-free realtime invalidations and refetches canonical state on reconnect. Activity-feed entries reference the same discussion ID and return persisted comment counts. Existing installations have an idempotent forward backfill for older CrewNow posts/feed rows. **Optional later:** add target authorization/integration for other apps, including Reviews.
- [ ] **Reactions** — Provide reusable reactions on supported objects. A reaction shown on an activity-feed item and on its originating app page must be the same reaction on the same canonical target, not separate per-view counts or records. Decide whether the initial scope is standard emoji, uploaded images, or another constrained set, and how reaction access follows the target object's permissions. **Depends on:** local user identity, durable reaction storage, a canonical-target/access contract from each participating app, and a defined reaction vocabulary. **Optional later:** Activity feed surfaces, Discussions, and Files if uploaded-image reactions are chosen.

## Integrations

### Inbound data connectors

- [ ] **Steam** — Fetch Steam user activity. Confirm whether the Games app also needs owned-game library data in the first integration slice, and how linked Steam accounts map to local users. **Depends on:** Steam account linking/mapping, External user activity's ingestion contract, and Tasks for background sync. **Optional later:** Games, if owned-game library data is included; that Games dependency is not settled.
- [ ] **Discord** — Fetch Discord user activity, subject to provider capabilities and an explicit mapping between Discord accounts and local users. **Depends on:** Discord account linking/mapping, External user activity's ingestion contract, provider access, and Tasks for background sync. **Optional later:** Notifications may use Discord as a separate outbound delivery channel; inbound activity collection does not require it.
- [ ] **Minecraft** — Fetch activity from a Minecraft server and map server identities to local users. **Depends on:** server access, server-identity mapping, External user activity's ingestion contract, and Tasks for background sync. **Optional later:** Stats or Newsletter can consume the persisted activity; neither is required for collection.

### Outbound publishing connector

- [ ] **Newsletter** — Produce a weekly or monthly newsletter and publish it to a configured webhook. Define which activity/data it summarizes, who configures it, and how scheduled generation and delivery failures are handled. **Depends on:** a configured webhook and an agreed content source; External user activity is needed if it summarizes provider activity, and Tasks support scheduled generation/delivery. **Optional later:** Activity feed or app-specific data if chosen as newsletter content; the sources are not yet decided.

The split above describes the current use cases, not a settled code architecture. Decide whether inbound account-linked data collection and outbound publishing need distinct integration contracts or lifecycle conventions. Provider-specific behavior belongs to integrations; integrations should use explicit platform/app contracts rather than writing directly to another module's tables.

## Possible future additions

- [ ] **Items, shop, and economy** — **Dependencies undecided:** define the item/catalog, ownership, and transaction model first. **Potential later links:** Profiles for user-facing inventories, Files for item artwork, and Notifications or Activity feed for purchase/ownership updates; none is established as required.
- [ ] **Profile customization and cosmetics** — Build on the shared profile and avatar presentation conventions above. **Depends on:** Profiles and its local user identity/profile model. **Optional later:** Files for uploaded assets and an Items/shop/economy system if cosmetics are earned or purchased.
- [ ] **Custom emoji** — **Dependencies undecided:** choose whether emoji are built-in or user-uploaded and define their scope/permissions. **Potential later links:** Files for uploaded emoji assets, and Reactions or Discussions if those systems support custom emoji; not required unless that integration is chosen.
- [ ] **Location sharing app** — **Dependencies undecided:** define location sources, sharing/access rules, and retention before selecting platform dependencies. **Potential later links:** Notifications for sharing alerts and Activity feed for carefully scoped updates, subject to explicit privacy rules.
- [ ] **Music scrobble endpoint and display app** — **Depends on:** user/account attribution and a durable activity contract; it could supply the External user activity system or expose an app-specific read model, which remains undecided. **Optional later:** Tasks for asynchronous processing and Stats or Newsletter as consumers.

## Dependency hints (not a priority order)

- External user activity plus task execution enables a first end-to-end provider sync and gives Stats and Newsletter data to consume; the Activity feed records actions within Gnaghome apps and is a separate use case.
- The Audit log is an administrative record of changes, not a social feed or analytics source; its admin-only access must be enforced by backend authorization.
- The Activity feed can begin without Discussions or Reactions. When those systems are added, feed entries link to app-owned objects, while comments and reactions stay canonical to those targets and obey the owning app's access rules.
- Files supports CrewNow image upload; it does not by itself imply shared folders or a general-purpose drive.
- Discussions and reactions may support Reviews, but Reviews' own rating/review model should be decided separately rather than assuming comments are reviews.
- Profiles and consistent user/avatar components are cross-app foundations. Cosmetic customization can remain future work.
- Calendar can be developed as an app without waiting for the provider activity pipeline.

## Decisions to make as work is sequenced

- Which app and integration form the first useful end-to-end slice? Which existing codebases are being ported, and what changes are needed to integrate them safely?
- What is the group-sharing model for each app, and which module owns each resource's authorization?
- What are the contracts for app-generated feed items and externally collected user activity, including attribution, retention, deletion, and any derived data?
- Which actions and fields must the Audit log capture, what retention and integrity guarantees are needed, and how should sensitive data be excluded while keeping audit-log reads admin-only?
- How should integrations be grouped: inbound per-user account mapping and sync versus outbound publishing, or one common contract with clear capabilities?
- What is the minimum files scope and storage target for the initial upload use cases?
- What guarantees and operational visibility should Tasks provide for retries, duplicate work, and failed jobs?
- How are notification delivery channels configured, and how do users control preferences and failures?
- Feed targets use a type-and-ID pair, with target types uniquely namespaced across apps; the owning app resolves the target and enforces access. When added later, how should Discussions and Reactions share the same canonical target across feed and object-page views while deferring to each app's access rules?
- Which activity types are recorded user actions versus generated or recurring items (such as calendar starts and birthdays), and what are their creation, visibility, and retention rules?
- What does a Review attach to, and what review/rating format is useful?
- What activity and sources should Newsletter summarize, and how are its cadence and webhook configured?
- What timezone, sharing, and editing rules does the group Calendar need?
