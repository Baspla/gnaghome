# Realtime gateway

Centrifugo channels represent authorization boundaries, not features. Authenticated clients receive grants for exactly `public` and `user:<userId>`. Publish information visible to all authenticated users on `public`; publish personal settings and notifications only to the affected user's channel. An `admin` channel may be introduced for privileged events if needed. Do not create feature-specific channels, device channels, or a global presence channel.

Every publication uses the shared `PlatformEvent` union in `shared/dto/platform-event.ts`: `{ id, occurredAt, type, action, entityId }`. `occurredAt` is a required ISO-8601 timestamp. Events carry no `data` property, including an empty object. The action is `CREATED`, `UPDATED`, or `DELETED`; `entityId` identifies a specific resource or an agreed collection/singleton (for example `activity-feed`, `custom-emojis`, `notification-settings`, `preferences`, or `crewnow-timeline`). The frontend validates each untrusted publication and dispatches it only to handlers registered for that event type.

Events are thin change signals, not state. Entity events identify the resource and operation; collection/singleton events prompt a matching visible view to refetch. The REST API and database remain authoritative. A consumer checks the entity ID against the data currently in its view before fetching: fetch a displayed entity by ID and patch/remove it, or refetch a matching visible collection/singleton. Silently ignore unrelated IDs and events while the consumer is not mounted. Refresh canonical data on reconnect to recover missed publications.

Keep publication best-effort after durable writes where practical. If Centrifugo is unreachable during local development, check that Docker and the Centrifugo container are running before treating it as an application issue.
